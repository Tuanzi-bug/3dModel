# Phase 3.2: Homepage 3D Preview & Web Adaptation - Context

**Gathered:** 2026-03-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 3.2 is a narrow inserted web polish phase before the mini-program work begins. It completes the landing-page hero 3D preview by replacing the current static placeholder with a lightweight interactive scene that enhances a stable poster-first hero. This phase does not attempt to bring the full editor to the homepage, does not expand into broad multi-page web responsiveness work yet, and does not begin the WeChat mini-program client itself.

</domain>

<decisions>
## Implementation Decisions

### Homepage preview scope
- **D-01:** Phase 3.2 only covers the homepage hero 3D preview area on the landing page.
- **D-02:** The current placeholder should be replaced with a real interactive 3D scene rather than another static illustration.
- **D-03:** Broader web adaptation beyond this homepage preview remains a later effort and is not part of this phase.
- **D-04:** Phase 4 mini-program work stays deferred until this homepage preview pass lands.

### Preview interaction model
- **D-05:** The hero preview uses a lightweight simplified cube rather than a full shelf model.
- **D-06:** The cube auto-rotates slowly by default to keep the hero visually alive.
- **D-07:** Users can drag to rotate and can zoom the preview, but they cannot pan the camera.
- **D-08:** Mobile follows the same interaction contract as desktop: rotate plus zoom are both supported.
- **D-09:** User interaction pauses auto-rotation, and auto-rotation resumes after a short idle delay.

### Visual direction and hinting
- **D-10:** The cube should feel product-adjacent rather than like a generic 3D demo; material cues may hint at shelf-like metal/wood usage even though the geometry stays simple.
- **D-11:** The preview may carry a slight marketing/showcase feel, but it should remain lightweight and subordinate to the homepage CTA/content.
- **D-12:** The preview includes a light interaction hint near or below the scene so users know they can drag and zoom.

### Loading, fallback, and motion safety
- **D-13:** The hero starts from a static poster-style visual and only upgrades into live 3D after the scene is ready.
- **D-14:** If WebGL is unavailable, initialization fails, runtime rendering errors occur, or the preview cannot run reliably, the hero must fall back to the static poster instead of showing a blank or broken 3D box.
- **D-15:** Loading, ready, and fallback states should keep the same visual footprint and composition center so the hero does not jump when states change.
- **D-16:** If the user prefers reduced motion, or the implementation determines the device should avoid continuous motion, auto-rotation should default to off while manual rotate/zoom interaction remains available.
- **D-17:** After the user stops interacting, the camera should gently return to the default showcase angle before auto-rotation resumes.

### Gesture, copy, and non-visual guardrails
- **D-18:** On touch devices, single-finger drag rotates the preview and two-finger pinch zooms it; the preview area should prioritize these 3D gestures while the user is actively interacting with it.
- **D-19:** Interaction hint copy should adapt by device type: desktop should reference drag plus wheel zoom, while touch should reference drag plus pinch zoom.
- **D-20:** The hero heading, supporting copy, and CTA buttons must remain immediately visible and usable before the 3D scene is ready; the preview is an enhancement layer, not a gate.
- **D-21:** This phase must not materially degrade the homepage's first-load feel in pursuit of the hero animation.

### the agent's Discretion
- Exact cube proportions, beveling, lighting, and material tuning.
- Exact idle duration before auto-rotation resumes after user interaction.
- Exact loading transition between poster and live 3D, as long as it remains subtle and stable.
- Exact responsive sizing and spacing inside the existing landing-page layout.
- The exact threshold for deciding when to suppress auto-rotation on weaker devices, as long as fallback and reduced-motion behavior remain deterministic.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `packages/web/src/components/editor/ViewportCanvas.tsx`: existing R3F + Drei control patterns for orbiting, zooming, and scene framing that can be adapted into a much simpler landing-page scene.
- `packages/web/src/components/editor/SceneRenderer.tsx`: material and lighting treatment in the editor can inform the hero scene's product-adjacent look without reusing editor-specific sceneGraph wiring.
- `packages/core/src/index.ts`: shared scene/types/template exports remain available if the planner decides any tiny reusable 3D helper belongs in shared code, though this phase does not require full scene-graph integration.
- `packages/web/src/app/page.tsx`: current landing page already has the right section structure, CTA placement, and placeholder container to upgrade in place.

### Established Patterns
- Web UI keeps Chinese copy and Tailwind utility styling aligned with `docs/design-system.md`.
- The repo already uses React Three Fiber and Drei in the editor, so a lightweight homepage scene can stay inside established runtime dependencies instead of introducing a new rendering stack.
- The landing page is currently desktop-first with `max-md:` adaptations; this phase should preserve that baseline rather than redesign the whole page.
- The web app already uses Vitest component tests and Playwright browser flows, so this hero preview should be planned with both component-level and browser-level regression coverage in mind.

### Integration Points
- The current hero placeholder block in `packages/web/src/app/page.tsx` is the insertion point for the new preview.
- Any lightweight 3D scene component should integrate into the landing page without pulling in editor-specific side panels, store wiring, or save/load logic.
- The interaction hint should live with the preview block, not as a separate global banner or modal.
- The poster and live 3D states should share a stable wrapper so the page layout does not shift when the enhancement loads or falls back.

</code_context>

<specifics>
## Specific Ideas

- "首页的3D预览区域需要完成" means this phase should ship a real hero preview, not leave a placeholder.
- "可以展示一个简易的立方体，用户可以进行缩放等等简单操作" means the preview should stay intentionally lightweight.
- "2，也可以自动缓慢旋转" locked the interaction model to auto-rotation plus user drag-rotate and zoom.
- "2，我觉得也需要一点点营销的展示" means the visual direction should feel polished and slightly promotional without becoming a heavy product video replacement.
- The chosen product-shaping approach is "poster-first + 3D enhancement" rather than "3D-first", so the hero remains stable before live rendering is ready.
- The static fallback should be a product-style poster/hero art direction, not a blank placeholder card.
- Reduced-motion users still keep manual interaction, but the continuous automatic motion should stop by default.
- After idle, the preview should return to its default showcase angle before resuming auto-rotation.
- Device-specific hint copy is part of the requirement, not an optional polish item.

</specifics>

- The WeChat mini-program client remains Phase 4 work after this inserted web phase is complete.
