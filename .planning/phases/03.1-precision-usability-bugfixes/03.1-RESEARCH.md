## User Constraints (from CONTEXT.md)

### Locked Decisions
### Snapping and movement
- Dragging should stay smooth during movement; snapping should resolve when the drag is released, not on every transform frame.
- On release, snapping should try compatible component-to-component anchors first and fall back to grid snapping only if no anchor match is available.

### CSV export compatibility
- BOM export remains a standard `.csv`, not `.xlsx` and not a custom text format.
- The exported file must stay comma-delimited and open directly in Excel with Chinese text intact.

### Viewport behavior
- Clicking empty space should only clear selection; it must not reposition the camera or zoom the scene.
- The viewport should add explicit toolbar actions for `聚焦选中`, `放大`, and `缩小`.

### Workflow constraints
- User-facing copy remains Chinese.
- Project runtime/build/test commands stay in Docker containers.
- Git operations stay on the host, not inside Docker.

- Exact release-event wiring between `TransformControls`, raw drag updates, and final snap resolution.
- Exact snap threshold tuning, as long as drag feel improves and anchor-first fallback-to-grid behavior is preserved.
- Exact Excel-safe CSV technique, as long as the file stays a comma-delimited `.csv`.
- Exact zoom step size and disabled behavior when no selection exists.

## Summary

Phase 3.1 should be planned as a narrow integration-repair phase, not as another feature expansion. The codebase already has the right underlying pieces: shared snap math in `packages/core`, pure BOM generation from canonical `sceneGraph` data, a viewport that already owns transform controls and preset views, and browser coverage that exercises the editor end-to-end. The regressions come from how those pieces were wired together in Phase 3.

The durable fix is:
1. Keep drag movement unsnapped while the user is actively manipulating the gizmo, then resolve anchor-first/grid-fallback snapping only when the drag completes.
2. Keep the exported BOM rows exactly as they are conceptually, but change the CSV serialization/download path to be Excel-safe for Chinese text.
3. Separate deselection from camera reframing, and add explicit viewport actions for focus and zoom in the existing toolbar pattern.
4. Update browser coverage to lock the repaired interaction model before the project advances to Phase 4.

**Primary recommendation:** Plan Phase 3.1 as 4 plans in 3 waves. Use Wave 1 for snap-on-release, Wave 2 for export compatibility plus viewport controls in parallel, and Wave 3 for browser regression coverage.

## Architecture Patterns

### Pattern 1: Snap Late, Persist Once
**What:** Keep raw drag motion responsive during pointer movement, then apply the canonical snap decision when the drag ends.
**When to use:** Transform gizmo movement in `ViewportCanvas`.
**Why:** Real-time magnetic snapping causes the exact pacing bug this phase is fixing.

### Pattern 2: Keep CSV Semantics in Core, Browser Download Thin
**What:** Generate BOM rows and CSV text in `packages/core`, while the header remains responsible only for the download UX.
**When to use:** Excel-safe BOM export.
**Why:** The format contract stays reusable and testable, while the web layer stays minimal.

### Pattern 3: Camera Actions Are Explicit and Ephemeral
**What:** Empty-space deselection should not imply any camera move; focus and zoom must be explicit viewport actions.
**When to use:** Selection changes, preset views, and the new focus/zoom buttons.
**Why:** View changes are inspection-only and should never feel like side effects of selection cleanup.

### Pattern 4: Browser Coverage Should Follow the Repaired Workflow
**What:** The end-to-end spec should reflect the new contract: drag first, snap on release, export Excel-safe CSV, deselect without jumps, then focus/zoom explicitly.
**When to use:** `precision-tools.spec.ts`.
**Why:** The existing browser spec currently encodes the old broken behavior.

## Common Pitfalls

### Pitfall 1: Still Snapping During `onObjectChange`
**What goes wrong:** Drag movement remains jumpy because the object keeps getting rewritten to snapped positions every frame.
**How to avoid:** Let `onObjectChange` persist raw movement, then snap once on drag end.

### Pitfall 2: Fixing CSV with MIME Type Alone
**What goes wrong:** `text/csv;charset=utf-8` on the Blob does not guarantee Excel will detect the encoding correctly.
**How to avoid:** Make the serialized download bytes explicitly Excel-safe while preserving comma delimiters and the `.csv` extension.

### Pitfall 3: Using Selection-Derived Bounds as an Automatic Camera Trigger
**What goes wrong:** Clicking empty space changes bounds from selected node to whole scene and causes an unwanted camera jump.
**How to avoid:** Decouple deselection from camera preset/focus effects; only explicit view actions should reposition the camera.

### Pitfall 4: Hiding Focus/Zoom Behind Non-Discoverable Gestures
**What goes wrong:** The user still cannot reliably recover a useful camera position during editing.
**How to avoid:** Put explicit `聚焦选中`, `放大`, and `缩小` controls in the existing viewport chrome.

### Pitfall 5: Leaving the Old Precision Browser Spec Untouched
**What goes wrong:** The repo keeps asserting the broken Phase 3 interaction contract and future regressions slip through.
**How to avoid:** Rewrite the spec around the repaired behavior, including download-byte assertions where needed.

## Codebase Reality Check

- `packages/core/src/utils/snap.ts` already provides reusable anchor-first/grid-fallback snap logic; the regression is caused by calling it on every transform change inside `ViewportCanvas`.
- `packages/web/src/components/editor/ViewportCanvas.tsx` currently calculates `bounds` from `selectedNodeId` with a whole-scene fallback, so deselecting changes `bounds` and retriggers `CameraPresetController`.
- `packages/web/src/components/editor/ViewPresetToolbar.tsx` already exists and is the right chrome surface to extend with explicit focus/zoom controls.
- `packages/core/src/utils/bom.ts` already builds correct BOM rows, but `serializeBomCsv()` currently returns plain CSV text only.
- `packages/web/src/components/editor/Header.tsx` currently downloads that plain text with `text/csv;charset=utf-8`, which is not enough to prevent Excel mojibake.
- `packages/web/tests/e2e/editor/precision-tools.spec.ts` currently asserts the old behavior by expecting a property-panel edit to snap immediately.
