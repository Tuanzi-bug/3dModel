<user_constraints>
## User Constraints (from CONTEXT.md)

### Locked Decisions
- Duplicating a component must keep the duplicate immediately editable in the properties panel.
- Duplicate IDs must remain compatible with the editor's typed `type-sequence` contract so labels, counters, and follow-up edits do not drift.
- Unsupported component-library entries must not behave like working actions.
- For now, only `杆` and `层板` are considered user-approved interactive component-library entries.
- Clicking the bottom-right coordinate-axis gizmo must not throw runtime errors.
- Preview images should move to a stable x-axis-oriented view while remaining deterministic from canonical `sceneGraph` data.
- Project commands, tests, and builds must continue running inside Docker containers.

### The agent's Discretion
- Exact disabled-state copy and visual treatment for unsupported entries.
- Exact duplication implementation shape, as long as selection continuity and typed IDs are preserved.
- Exact SVG styling for the x-axis preview projection.

### Deferred Ideas (OUT OF SCOPE)
- Snapping, dimension aids, preset views, LED strip support, back panel support, and BOM export remain Phase 3 work.
</user_constraints>

<research_summary>
## Summary

This phase is a local codebase hardening pass, not an ecosystem research problem. The bugs are directly traceable to current implementation mismatches introduced during Phase 2: duplication still uses raw `nanoid()` IDs in `packages/core/src/utils/scene-tree.ts`, the store does not retarget selection after duplicate, the component panel still exposes entries beyond the user-approved support boundary, `ViewportCanvas.tsx` wires `GizmoHelper` without making `OrbitControls` the default control context, and `scene-preview.ts` projects the scene with a pseudo-isometric bias instead of the requested x-axis side view.

The highest-leverage fix is to treat each bug as a contract mismatch with an existing source of truth. Duplication should flow through the same typed ID/counter strategy the store already uses for new components. The component panel should declare support status explicitly instead of implying that every listed entry works. The gizmo should read from a valid default control context and tolerate null/deselected transitions. The preview generator should keep its pure SVG approach, but change the projection math and per-node silhouette rendering to reflect an x-axis-oriented view.

**Primary recommendation:** insert a narrow Phase 2.1 with four plans that directly map to the four reported bugs, using local TDD and targeted Playwright coverage rather than broad architecture changes.
</research_summary>

<codebase_findings>
## Codebase Findings

### Duplicate/edit continuity
- `packages/core/src/utils/scene-tree.ts` currently clones duplicated nodes with `generateId()`, which produces opaque `nanoid()` strings rather than typed `type-sequence` IDs.
- `packages/web/src/stores/editor-store.ts` currently updates `sceneGraph` on duplicate but does not retarget `selectedNodeId` to the duplicated node and does not integrate duplication with typed counter generation.
- `packages/web/src/components/editor/NodeParamsEditor.tsx` depends on `findNode(sceneGraph, selectedNodeId)` and `parseNodeId(node.id)`, so invalid IDs or stale selection can make the properties surface misleading or empty.

### Component-library support boundary
- `packages/web/src/components/editor/ComponentPanel.tsx` currently exposes seven component entries.
- `packages/web/src/components/meshes/registry.ts` does not register `ledStrip` or `backPanel`, and the user explicitly narrowed the supported set further to only the first two entries for now.
- There is no single support manifest tying panel affordances to actual renderer/runtime support.

### Viewport gizmo/runtime stability
- `packages/web/src/components/editor/ViewportCanvas.tsx` renders `<OrbitControls ref={orbitControlsRef} ... />` but does not set `makeDefault`.
- The same file renders `<GizmoHelper><GizmoViewport /></GizmoHelper>`, which in Drei expects a valid control context when clicked.
- The reported runtime errors mentioning `'getTarget' in null` and `'minPolarAngle' in null` are consistent with a gizmo trying to inspect a missing control object.
- `selectedGroup` is stored in component state and can become stale across deselect/unmount transitions if not explicitly cleared.

### Preview fidelity
- `packages/core/src/utils/scene-preview.ts` currently uses `x * 72 - z * 30` and `y * 64 - z * 18`, which creates a pseudo-isometric projection.
- The current preview still succeeds as a deterministic SVG data URL generator and is already wired through template metadata plus design create/update routes.
- Changing the projection math inside the pure generator is lower risk than replacing the preview pipeline with live canvas capture or a new asset system.
</codebase_findings>

<architecture_patterns>
## Recommended Patterns

### Pattern 1: Store-owned duplication contract
Implement duplication as a store-level contract that:
- regenerates duplicate subtree IDs using the typed counter strategy,
- returns or captures the duplicated root ID,
- and sets `selectedNodeId` to the duplicate so the properties panel stays continuous.

### Pattern 2: Explicit support matrix
Represent library availability as data rather than implicit behavior. The panel should render enabled and disabled entries from the same catalog, with only approved entries clickable.

### Pattern 3: Default-control gizmo wiring
Treat the viewport gizmo as a consumer of the default camera controls. Make `OrbitControls` the default control source and add null-safe cleanup around selection and control refs.

### Pattern 4: Side-profile SVG projection
Preserve the current deterministic SVG approach, but project from an x-axis-oriented side view so horizontal placement primarily reflects `z` and vertical placement reflects `y`, with per-component silhouettes sized from actual node params.
</architecture_patterns>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Fixing duplicate selection without fixing duplicate IDs
This would make the duplicate editable temporarily, but node labels, counters, and future additions would continue drifting.

### Pitfall 2: Hiding unsupported components instead of declaring them
This would reduce immediate errors but leave no explicit support boundary for later re-enablement.

### Pitfall 3: Adding null guards without wiring a real control context
This can suppress one crash path while leaving gizmo clicks broken or inert.

### Pitfall 4: Making the preview more decorative instead of more truthful
The user's complaint is recognizability, not lack of gradients. The projection math matters more than added styling.
</common_pitfalls>

<open_questions>
## Open Questions

1. **Should unsupported entries stay visible or disappear?**
   - What we know: the user asked to disable them first, not remove them.
   - Recommendation: keep them visible but disabled with clear Chinese status copy so the roadmap boundary remains explicit.

2. **Where should typed duplicate-ID regeneration live?**
   - What we know: the core helper currently duplicates generically, but only the store owns the typed counter state.
   - Recommendation: let the store own the final duplicate-ID contract, either by extending the core helper with a generator callback/result object or by post-processing the duplicate subtree through existing typed-ID utilities.
</open_questions>
